# ADR 0001：阶段 0 本地技术栈

- 状态：已采纳（2026-10-10，依据 M0 spike，详见 `../spike-results.md`）

## 决策

| 主题 | 决定 | 依据 |
|---|---|---|
| 运行形态 | 纯本地、单用户；不用 Celery、Redis，不做鉴权 | 用户决定 |
| Python | 3.11（由 uv 管理） | music21 10 要求 ≥3.11 |
| 钢琴转录 | Transkun 2.0.1，默认跑 MPS，失败时自动回退 CPU | 与 CPU 输出完全一致，快约 1.37 倍，显存 3.65 GB；自带延音和柔音踏板 |
| 节拍追踪 | beat_this 1.1，跑 CPU | 约 2 秒；MPS 与 CPU 结果一致；MIT 许可 |
| 数据源 | ScoreDoc JSON（时间单位为 tick，PPQ=960） | OSMD 只能显示；所有输出都由 ScoreDoc 确定性生成 |
| PDF | MuseScore 4 CLI；判定成功的标准是「新输出文件存在且非空」 | musicxml2ly 不维护；MuseScore 无界面模式退出时崩溃，但发生在写完文件之后 |
| 任务执行 | SQLite（WAL）任务表 + 单个 worker；每个 ML 阶段在独立子进程里运行，并有 RSS 看门狗 | 16 GB 内存：同一时间只有一个模型；进程退出即释放内存 |
| 缓存 | 只缓存 S1 转录和 S2 节拍（键为音频 sha + 引擎版本）；S3–S6 每次重算 | S3–S6 是纯 Python，只需毫秒级；改先验参数重跑约 1 秒 |
| 进度 | 前端每秒轮询 | 实现简单，刷新页面后也能接上 |

## 与原计划的差异

- 原计划给 S3（节拍）和 S4（量化）分别做缓存。改为合并后不缓存，原因有两个：一是太快，缓存不值得；二是复合拍的判断需要先知道量化结果（见 ADR 0004）。
- music21 导出时关闭 `makeNotation`。休止符、连音线、符杠、三连音括号和临时记号都由我们自己生成，这样渲染时间从 1.5 秒降到 0.4–0.5 秒（Chopin，1105 个音符）。
- `/render/musicxml` 和 `/render/idmap` 按渲染目录加锁，避免两个并行请求重复渲染同一份乐谱。加锁后编辑到预览的时间为 1.28 秒，包含 0.6 秒的保存防抖。
